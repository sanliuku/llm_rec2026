# LLM 推荐模型效率指标汇总

数据来源：各模型 `runs/<dataset>/results/<run_id>/metrics.json`（训练脚本内 `torch.cuda.max_memory_allocated()` + `perf_counter` 实测写入），
逐 run 原始值见 `results/model_efficiency_runs.csv`。

## 口径

| 项 | 定义 |
|---|---|
| 总参数量 | `sum(p.numel() for p in model.parameters())`，含冻结主干（Qwen2.5-1.5B 或 SASRec+BGE） |
| 可训练参数量 | `requires_grad=True` 的参数（LoRA / adaptor / 解冻的 SBERT） |
| 训练时间 | `trainer.train()` 墙钟时长（不含数据准备），单卡单 run 全程 |
| 推理时延 | **单用户 batch=1** 端到端（拼 embedding + 自回归生成），`max_new_tokens=16`，warmup 3 次、重复 20 次取均值，单位 ms/用户 |
| 峰值显存 | `torch.cuda.max_memory_allocated()`，GiB；训练峰值在 trainer 结束后读，推理峰值在释放训练态并 `empty_cache()` 后重新 reset 再测 |

聚合方式：同模型同数据集多次 run（不同 seed）取 **均值±标准差**，并给出中位数与区间。

## 需要注意的几点

1. **ALLMRec_old 的参数量口径不同**：`106,872,832` 是「冻结 CF(SASRec-concept，约 4.34M) + align MLP(263,424) + BGE-base-zh(102,267,648)」整体；可训练的 102,531,072 中 102,267,648 是被在线微调的文本编码器，只有 263,424 是新增对齐层。它不是 LLM 生成式模型，所以不能和其它 5 行的 1.5B 直接比。
2. **ALLMRec_old 无时延/显存记录**：该模型训练脚本（`ALLMRec_old/train_mooc_align.py`）没有埋训练时长、时延、峰值显存，`metrics.jsonl` 只记录 loss/指标，`train.log` 无时间戳，文件 mtime 不可作为训练时长依据。需要补测才能填这三格。
3. **推理时延方差偏大，建议用中位数**：同一模型同一配置的不同 seed run 之间，时延可差 2–7 倍（如 LLaRA_old mid：268 ms vs 1819 ms；LLaRA small 反而只有 930–933 ms）。训练时长也呈双峰（如 LLaRA_old mid：32.1 h 与 52.4 h 两组）。两者都指向**共享 GPU 抢占**，而不是模型差异。论文表格建议用中位数，或重测时独占卡。
4. **LLaRA 的 mid_data 与 small_data 可训练参数不同（3.84M vs 11.98M）**：mid_data 的 4 个 run 是较新代码（11-18/19），只训 LoRA+adaptor；small_data 的 run 更早（11-15/18），额外训了 token embedding 表。主表取新代码口径。
5. **LLaRA_old 训练时间最长（44.1 h）但显存最低（7.23 GB）**，因为 batch=24 且主干全冻；ALLMRec_llm 显存最低（6.46 GB，LLM 全冻无 LoRA），但时延最高（2437 ms），因为每个用户都要走完 Qwen2.5-1.5B 全量前向 + 16 token 生成。

## 命名澄清

工程里同时存在 `ALLMRec_old/`（A-LLMRec 论文原版复现：CF 冻结 + SBERT 在线对齐 + 对齐 MLP，非 LLM）和 `ALLMRec_llm/`（按官方 `ghdtjr/A-LLMRec` 重写：Qwen2.5-1.5B 全冻 + 5.32M adaptor + NLL）。
两者是不同模型，不是同一模型的别名，主表把两行都列出。若论文中的「ALLMRec_old」指的是官方代码复现版，请用 **ALLMRec_llm** 那一行。
